# 产品与架构约定

状态：架构目标。alpha.1 已实现其中的单人基础窗口、手动/物品/技能检测和原生进度记录；其余能力仍是路线规划。当前实现与验收结果以 README / TESTING 为准。

## 玩家体验

章节列表、任务关系图、说明面板与最多三个追踪任务构成主界面。任务状态同时使用文字、图标和颜色，默认静音。支持缩放、大字体、简体中文和英文；4K 与普通分辨率都列入验收。

任务推动玩家安家、学习系统、准备远征和重建基础设施。玩家可以提前行动；任务条件锁定只约束结算，不限制游戏操作。已完成事实尽量补认。

## 分层

| 层 | 职责 | 禁止依赖 |
|---|---|---|
| 定义与注册 | 任务包、章节、任务、条件、奖励与本地化 | 当前角色和世界对象 |
| 纯逻辑核心 | 依赖图、状态转换、条件聚合、迁移规划 | 游戏 UI、第三方全局对象 |
| PZ 适配 | 角色、物品、技能、位置、事件与存档读写 | 具体任务包剧情 |
| 可选模组适配 | 将第三方状态转换成稳定能力结果 | 任务窗口 |
| UI | 展示、追踪、确认、领取请求和故障说明 | 绕过核心直接改存档或发奖励 |
| 内容包 | 教学文案、关系、目标、奖励与布局 | 自行注入未声明的运行代码 |

优先 Lua 实现游戏层，不要求核心安装 ZombieBuddy 或图形模组。实际接口通过现有 B42 Lua 与游戏测试确认，不把设计中的函数名当作已存在的游戏 API。

## 判定接口

检测结果使用四态：`met`（满足）、`unmet`（未满足）、`unavailable`（依赖缺失）、`error`（检测失败）。后两者不能被当作满足，也不能静默变成零进度。

第一阶段：手动确认、技能阈值、物品持有。后续：位置、制作/维修事件、建筑和设施状态。每种条件定义持有还是消耗、是否可追溯、事件计数从何时开始、适用角色/世界范围。

物品检测应支持等价集合和嵌套容器，明确是否检查背包、附近容器或车辆；同一组要求的数量不能由同一物品重复满足。制作事件不能仅凭持有物品推断。

适配器先注册能力，再由任务包声明使用。例如 `epr.facility_operational` 和 `epr.building_service` 是本项目拟定的能力名，不是 EPR 已存在的 API。

事件触发后只评估受影响的任务；持有与位置状态使用限频检查。禁止每帧遍历所有容器、任务和世界对象。性能预算在游戏原型测量后确定。

## 任务状态

`locked → available → completed → claimed`；无物资奖励的任务完成后无需人为领取。外加明确的 `unavailable` / `error` 展示状态。任务完成记录与奖励领取记录分离；先完成后解锁可以缓存事实，但结算前仍遵守依赖关系。

手动确认是公开的任务类型，不冒充自动检测。故障修复入口单独记录修正原因和时间，不与正常确认混用。

## 持久化与更新

分别记录 `frameworkVersion`、`schemaVersion`、`saveVersion` 和 `packVersion`。稳定键由命名空间和 ID 构成；翻译、标题或排序变化不能清空进度。

- 世界进度：据点登记、工程、探索里程碑与相应奖励账本。
- 角色进度：技能、个人教学与角色范围奖励；同一世界新角色重新检查。
- 任务事实：区分当前状态与历史事件。不能补认的旧事件明确标注并允许受控确认。
- 删除任务：保留旧记录为归档，不重用 ID，不自动撤回已发放物品。
- 缺失内容包：保留其进度，暂停相关任务；重新启用可恢复。
- 迁移：先备份再变更，记录迁移版本；失败保持原数据并显示恢复入口。
- 降级：检测新存档格式，拒绝破坏性写回，给出备份恢复说明。

禁止将模组载入顺序、章节下标或玩家显示名称用作稳定身份。

## 奖励与故障恢复

以世界/角色范围和稳定任务奖励 ID 记录领取。背包容量不足时保持待领取；连点、重进和升级都要测试。

写领取标记与发放游戏物品之间通常不能假设存在跨系统事务。设计需包含领取意图、发放结果及恢复检查，并在实现阶段通过强制中断验证。无法确认是否发放时转为待核对状态，避免盲目再发；不能提前声称实现了严格恰好一次。

单人版不进行反作弊惩罚。未来联机版由服务端判定和发奖，客户端只提交请求；服务端未实现前不标记支持联机。

## 发行拆分

先单仓库维护，减少版本协调负担。未来构建独立的 Core、Demo、Alpharius 内容与可选适配模组。Core 发布包只包含通用能力，Alpharius 内容不会自动改变玩家沙盒设置。

工坊 ID 与 GitHub URL 在真实创建后补入，不使用虚构地址。公开包仅含本项目原创或有明确再分发授权的文件。
